# Architecture Decision Records

Фиксируем ключевые технические решения и причины их принятия.
Формат: ADR-NNN, дата, контекст, решение, альтернативы, последствия.

---

## ADR-001: Монорепо Next.js вместо раздельных frontend/backend

**Дата:** старт проекта
**Статус:** принято

**Контекст:**
Нужно выбрать между монорепо (Next.js + tRPC) и раздельной архитектурой (Next.js frontend + NestJS backend).

**Решение:** монорепо Next.js + tRPC.

**Причина:**
- Один язык, один репозиторий, один деплой
- End-to-end типизация без кодогенерации — типы из Prisma идут прямо в компоненты
- Соло-разработчик: не нужно поддерживать два приложения, два CI, два набора переменных окружения
- Скорость разработки выше на 2–3x для MVP

**Альтернативы:**
- NestJS backend — модульная архитектура, лучше масштабируется, но overhead для соло
- REST + OpenAPI — больше boilerplate, нужна кодогенерация клиента
- GraphQL — избыточно для MVP, сложнее кэширование

**Последствия:**
При росте команды до 5+ человек или появлении мобильного приложения — рассмотреть выделение API в отдельный сервис.

## ADR-002: tRPC вместо REST API

**Дата:** старт проекта
**Статус:** принято

**Контекст:**
Нужен типобезопасный API между серверной и клиентской частью.

**Решение:** tRPC v11.

**Причина:**
- Полная типизация без кодогенерации
- Zod-валидация на входе каждой процедуры
- React Query интеграция из коробки (кэш, loading states, invalidation)
- Разделение на `query` / `mutation` явно описывает намерение

**Альтернативы:**
- REST + Zod — типизация только на стороне сервера, клиент пишет типы вручную
- GraphQL + codegen — мощнее, но значительно сложнее для соло

## ADR-003: Clerk для авторизации

**Дата:** старт проекта
**Статус:** принято

**Контекст:**
Нужна авторизация с поддержкой email, OAuth, управлением сессиями.

**Решение:** Clerk.

**Причина:**
- Полностью управляемый сервис — ~2 часа настройки против нескольких недель самописной auth
- Бесплатный тир: 10 000 MAU
- Встроенный UI для sign-in / sign-up
- Webhook при регистрации → синхронизация с нашей БД через `auth.syncUser`
- Поддержка metadata для хранения роли пользователя

**Альтернативы:**
- NextAuth.js — open source, но больше кода, нет готового UI
- Lucia — более низкоуровневый, полный контроль, но дольше разрабатывать

**Последствия:**
Зависимость от внешнего сервиса. При отказе от Clerk потребуется миграция сессий.

## ADR-004: Один аккаунт с переключением роли

**Дата:** обсуждение функционала
**Статус:** принято

**Контекст:**
BIM-специалист может одновременно быть фрилансером (выполняет заказы) и заказчиком (нанимает других). Нужно решить: один аккаунт или два.

**Решение:** один аккаунт, переключение роли (`UserRole: FREELANCER | CLIENT`) в настройках профиля.

**Причина:**
- Удобство для пользователя — не нужно выходить и заходить в другой аккаунт
- Реалистично для BIM-рынка: ГИП может и фрилансить, и нанимать субподрядчиков

**Последствия:**
- `clientProcedure` и `freelancerProcedure` проверяют **текущую активную роль**, а не просто факт наличия профиля
- При переключении роли — обновляется `user.role` в БД и metadata в Clerk
- UI адаптируется: при роли CLIENT показывается интерфейс заказчика, при FREELANCER — фрилансера

## ADR-005: PostgreSQL FTS вместо Elasticsearch

**Дата:** обсуждение поиска
**Статус:** принято (пересмотреть при > 10k анкет)

**Контекст:**
Нужен поиск фрилансеров по навыкам, специализации, местоположению.

**Решение:** PostgreSQL Full-Text Search через `tsvector` и триггеры.

**Причина:**
- Нет дополнительного сервиса и инфраструктуры
- Для MVP (< 10k анкет) производительности хватит
- Supabase поддерживает FTS нативно

**Реализация:**
```sql
-- Триггер на freelancer_profiles
CREATE OR REPLACE FUNCTION update_profile_search_vector()
RETURNS trigger AS $$
BEGIN
  NEW."searchVector" :=
    setweight(to_tsvector('russian', coalesce(NEW.title, '')), 'A') ||
    setweight(to_tsvector('russian', coalesce(NEW.bio, '')), 'B') ||
    setweight(to_tsvector('simple', array_to_string(NEW.skills, ' ')), 'A') ||
    setweight(to_tsvector('russian', array_to_string(NEW.specializations, ' ')), 'A');
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER profile_search_vector_update
  BEFORE INSERT OR UPDATE ON freelancer_profiles
  FOR EACH ROW EXECUTE FUNCTION update_profile_search_vector();
```

**Альтернативы:**
- Elasticsearch — мощнее, но отдельный сервис, сложнее деплой
- Typesense — проще Elasticsearch, хорошая альтернатива при росте

## ADR-006: Stream Chat для мессенджера

**Дата:** обсуждение функционала
**Статус:** принято

**Контекст:**
Нужен чат между фрилансером и заказчиком по конкретному заказу/контракту.

**Решение:** Stream Chat SDK.

**Причина:**
- Бесплатный тир: 5M сообщений/месяц
- Готовые React-компоненты
- Realtime из коробки — не нужно строить WebSocket инфраструктуру
- Сохранение истории, индикаторы прочтения, typing indicators

**Ограничения:**
- Чат привязан к конкретному отклику или приглашению (не свободное общение)
- Stream channel создаётся при `proposal.create` или `invitation.accept`

**Альтернативы:**
- Socket.io — нужен отдельный сервер, хранение сообщений в БД — ~2 недели работы
- Supabase Realtime — проще, но беднее функционал чата

## ADR-007: ЮKassa без эскроу на старте

**Дата:** обсуждение платежей
**Статус:** принято

**Контекст:**
Решить, держать ли деньги на эскроу до завершения работы.

**Решение:** эскроу не реализовывать на MVP, оплата напрямую между пользователями.

**Причина:**
- Эскроу требует статуса платёжного агента или НКО в РФ
- Юридическая и техническая сложность неоправданна для MVP
- Хранить деньги на балансах пользователей без лицензии — серая зона

**Монетизация платформы:**
- Подписка для заказчиков (публикация вакансий): FREE / STARTER / PRO / UNLIMITED
- Подписка для фрилансеров (продвижение анкеты): FREELANCER_PRO
- Разовая публикация: ONE_TIME_POST (без подписки, чуть дороже в пересчёте)

**Последствия:**
Эскроу — запланированная фича следующей итерации. Схема Prisma уже подготовлена к его добавлению.

## ADR-008: Модерация вакансий и профилей

**Дата:** обсуждение функционала
**Статус:** принято

**Контекст:**
Нужно ли проверять вакансии и профили перед публикацией?

**Решение:** ручная модерация администратором перед публикацией.

**Жизненный цикл:**
```
Profile: DRAFT → PENDING → PUBLISHED
                        → SUSPENDED (модератор заблокировал)
Job:     DRAFT → PENDING → PUBLISHED
                        → DRAFT (отклонено, возврат слота/денег)
```

**Причина:**
- BIM-ниша — профессиональный рынок, качество анкет важно
- Нужна защита от спама и фейков
- Верификация документов (паспорт, BIM-сертификаты) — только вручную

**Последствия:**
Нужна очередь в админке. При отклонении вакансии — возврат слота подписки или денег (если разовая оплата).
